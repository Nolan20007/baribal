## 1. Самое главное: не смешивать два разных типа фотографий

У каждой карточки есть два независимых набора:

- **Обложка** — фотография, видимая сразу в плитке карточки на странице `/foto/`.
- **Галерея** — дополнительные фотографии, которые открываются после нажатия «Все фото».

Наличие фотографий галереи НЕ означает, что у карточки есть обложка. Наличие обложки НЕ означает, что галерея перенесена. Проверять и публиковать их отдельно.

**Не использовать этот workflow как универсальный импортёр для других диапазонов:** он специально написан для первых десяти карточек.

### Карточки 51–60

Это подтверждённая последовательность из трёх этапов:

1. Получение/диагностика исходных адресов: [run 44439696580](https://github.com/Nolan20007/baribal/actions/runs/44439696580), workflow `.github/workflows/diagnose-creatium-originals.yml`, скрипт `maintenance/tools/diagnose-creatium-originals.mjs`.
2. Проверка кандидатов: [run 44440127175](https://github.com/Nolan20007/baribal/actions/runs/44440127175), workflow `.github/workflows/verify-cover-candidates-batch.yml`.
3. Импорт только одобренных обложек: [run 44440229920](https://github.com/Nolan20007/baribal/actions/runs/44440229920), workflow `.github/workflows/import-approved-cover-batch.yml`.

**Порядок обязателен:** получить кандидатов → проверить оригиналы → вручную подтвердить соответствие каждой фотографии карточке → внести подтверждённые URL в `maintenance/cover-approved.json` → запустить импорт одобренных обложек. Нельзя пропускать визуальное подтверждение или импортировать весь список кандидатов автоматически.

### Важное ограничение диагностического скрипта

`diagnose-creatium-originals.mjs` формирует диагностический отчёт и извлекает адреса галереи. Его поле `mainImageUrl` нельзя автоматически считать правильной обложкой. В диагностике оно может указывать на видимое превью. Для обложки нужен подтверждённый полноразмерный оригинал, визуально соответствующий именно этой карточке.

Workflow проверки кандидатов проверяет загрузку, формат, размер и вес файла. Это техническая проверка, а НЕ доказательство, что на фотографии изображён правильный автомобиль/проект. Это подтверждает человек по артефакту.

### Карточки 61–80 и последующие партии

Для 61–80 применялась та же логика списка одобренных URL и импорта: источник подтверждённых URL хранится в `maintenance/cover-approved.json`, импорт выполняет `.github/workflows/import-approved-cover-batch.yml`. История импорта: [run 44440229920](https://github.com/Nolan20007/baribal/actions/runs/44440229920) — это пример для 51–60; для каждой новой партии сначала найти и проверить соответствующий успешный run.

Не считать любой workflow с похожим названием автоматически подходящим. Перед запуском открыть его YAML и прочитать все команды. Если диапазон, входной JSON или поведение отличаются от проверенного процесса — остановиться и сначала сверить с эталоном 51–60.

## 4. Запрещённые действия

- Не использовать универсальный экстрактор `extract-creatium-images.mjs` и не восстанавливать его workflow.
- Не использовать универсальный Playwright-скрипт, который автоматически угадывает обложку по самому большому видимому изображению.
- Не считать `mainImageUrl` из диагностического JSON подтверждённой обложкой.
- Не считать превью Creatium вида `267x200q8` или `356x200q8` оригиналом.
- Не выбирать первую фотографию галереи как обложку без отдельной визуальной проверки.
- Не скачивать и не привязывать фотографии из общей сетки проектов вместо активной галереи нужной карточки.
- Не смешивать обложки и галереи, их JSON, папки, workflow и критерии готовности.
- Не менять существующие рабочие скрипты «для удобства», не переименовывать и не удалять их без проверки зависимостей.
- Не запускать workflow, пока не прочитан его YAML и не проверены входные данные.
- Не работать в `test-project`. Рабочая ветка только `main`.

## 5. Обязательный порядок работы с каждой новой партией

### Перед началом

1. Прочитать этот файл целиком.
2. Прочитать `AGENTS.md`.
3. Уточнить, что именно переносится: **обложки** или **галереи**. Не выполнять оба вида работ одним непроверенным процессом.
4. Посмотреть историю GitHub Actions для ближайшей успешно опубликованной партии того же типа.
5. Открыть успешный workflow YAML, скрипты, manifest/JSON и результат run. Убедиться, что понимаешь, какие конкретно входы и выходы использовались.
6. Проверить, что рабочая ветка `main`; не трогать `test-project`.

### Для обложек

1. Получить URL-кандидаты диагностикой, не назначая их обложками автоматически.
2. Скачать и проверить оригиналы: HTTP успешен, реальный файл изображения, размеры не меньше 500×300, размер файла больше 20 KB.
3. Проверить каждое изображение визуально и сверить с текстом/автомобилем нужной карточки. Неподтверждённые URL не включать в approved manifest.
4. Записать только вручную подтверждённые URL в `maintenance/cover-approved.json` с правильными `cardIndex` и описанием.
5. Запустить проверенный workflow импорта одобренных обложек. Он должен отказать при неверном числе карточек, уже существующей обложке, невалидном оригинале или провале post-check.
6. Проверить diff: изменены именно нужные карточки, имена файлов и пути правильные, ни одна чужая карточка не затронута.

### Для галерей

1. Открыть именно карточку нужного номера на старом сайте и её активную галерею.
2. Получить оригинальные URL только из этой галереи по проверенной процедуре клика по миниатюрам/просмотра оригинала.
3. Проверить число фотографий и размеры каждого оригинала; превью и дубли исключить.
4. Вручную проверить, что все фотографии принадлежат нужному проекту и порядок не перепутан.
5. Скачать и подготовить файлы, обновить только соответствующие данные галереи.
6. Проверить, что обложка не подменена фотографией из галереи и что существующие карточки не сдвинулись.

### После изменений и публикации

1. Проверить diff и список изменённых файлов до коммита.
2. Дождаться завершения нужного Actions run. Не путать его с диагностическим или старым запуском.
3. Дождаться отдельного deploy workflow GitHub Pages.
4. Открыть опубликованную страницу `https://nolan20007.github.io/baribal/foto/`.
5. Проверить каждую карточку партии на опубликованном сайте: правильный номер, правильная обложка, загрузка файла без ошибки. Для галерей открыть каждую проверяемую карточку и проверить фотографии/порядок.
6. Проверить прямые URL файлов и отсутствие ошибок загрузки. Если опубликованную страницу нельзя проверить, честно указать, что публикация не подтверждена.

## 6. Критерии статуса

- **«Готово и опубликовано»** — только после проверки опубликованного сайта и фактического отображения.
- **«Файлы/код готовы, сайт не проверен»** — коммит или Actions успешны, но опубликованная страница ещё не проверена.
- **«Не готово»** — есть ошибки, неподтверждённые фотографии, неверные соответствия или отсутствует публикация.

Зелёный Actions, существующий файл, заполненный JSON и успешный коммит по отдельности НЕ доказывают, что пользователь видит правильное фото на сайте.

## 7. Как действовать, если что-то не совпадает

**Остановиться. Не выдумывать обходной способ.** Сверить конкретный шаг с успешным run и его исходниками. Если эталон не отвечает на вопрос, сообщить, чего именно не хватает, и запросить решение до изменения файлов. Никаких экспериментов на основной странице и никаких массовых запусков наугад.

Сначала прочитай эту инструкцию и `AGENTS.md`. Затем найди успешный run для такого же типа фотографий и диапазона, изучи workflow, скрипт и входные данные. Повтори подтверждённый процесс. Не изобретай новый. Не смешивай обложки с галереями. Не называй работу готовой без проверки опубликованного сайта.
