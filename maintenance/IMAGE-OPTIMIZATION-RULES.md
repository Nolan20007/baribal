# ОБЯЗАТЕЛЬНЫЕ ПРАВИЛА ОПТИМИЗАЦИИ ИЗОБРАЖЕНИЙ BARIBAL

Последнее обновление: 22 ноября 2026. Рабочая ветка: `main`.

Эта инструкция действует для ВСЕХ страниц и компонентов сайта: главной, услуг, портфолио, видео, студии, форм, общих виджетов и новых страниц. Она дополняет, но не заменяет `PHOTO-MIGRATION-RULES.md`: правила происхождения и соответствия фотографий портфолио остаются обязательными отдельно.

## 1. Главное правило

Нельзя добавлять растровое изображение в опубликованную HTML-страницу только потому, что файл существует или уже имеет формат WebP. Нужно подготовить подходящий размер файла для фактического размера отображения и подключить адаптивную загрузку.

**Каждое новое или заменяемое растровое изображение до публикации должно пройти все этапы:**
1. Проверить исходник, формат, реальные размеры, вес, прозрачность и визуальное качество.
2. Сохранить исходник/полноразмерный оригинал, если он нужен для лайтбокса, галереи или дальнейшего использования.
3. Подготовить оптимизированную версию WebP (или AVIF с совместимым fallback, если это оправдано) и адаптивные размеры под реальные варианты отображения.
4. Подключить `srcset` и корректный `sizes` там, где изображение может отображаться в разных размерах. Для единственного фиксированного маленького элемента подготовить отдельный файл нужного размера.
5. Указать реальные атрибуты `width` и `height`, осмысленный `alt` (пустой только для декоративного изображения), подходящий `loading` и `decoding`.
6. Проверить на опубликованной странице, что браузер выбирает ожидаемый небольшой ресурс на телефоне и более крупный на широком экране; проверить PageSpeed после публикации.

## 2. Адаптивные версии

- Не отдавать файл 1600–2000 px в карточку, которая отображается примерно в 300–400 px, если можно подготовить подходящий вариант.
- Для контентных фотографий обычно готовить варианты примерно 400, 800, 1200 и 1600 px по ширине. Не увеличивать исходник: максимальный вариант не должен превышать реальное разрешение оригинала.
- Набор вариантов и `sizes` выбирать по CSS-геометрии конкретного блока, а не копировать одну формулу на все страницы.
- Для карточек/плиток использовать лёгкие варианты, соответствующие их колонке на мобильном и desktop.
- Для широких изображений первого экрана/крупных секций подбирать отдельный набор размеров с учётом фактической ширины контейнера.
- Если элемент всегда показывается в одном небольшом размере (например, иконка 24×24), не использовать фотографию 350×350: подготовить отдельный небольшой ресурс с достаточным запасом для экранов высокой плотности (обычно около 48–96 px).


### Отдельное правило для фото в плавающем виджете связи

- Для круглой фотографии свёрнутой кнопки и фотографии в заголовке раскрытой панели используется **один и тот же квадратный оригинал `foto/foto.png` (350×350)**. Не подменять его вертикальными портретами `foto1.png`, `foto2.png` или `foto3.png`: пользователь должен видеть одну и ту же фотографию в обоих состояниях виджета.
- CSS обрезает общий квадратный оригинал до круглого изображения; сохранять согласованные размеры и кадрирование кнопки, не менять фотографию или `object-position` без отдельного запроса и визуальной проверки на телефоне и ПК.
- Сборщик создаёт для `foto/foto.png` адаптивные WebP-версии с повышенным качеством **92** (вместо общего качества 80); оригинал остаётся в репозитории.
- Для фотографии в свёрнутой кнопке использовать `sizes: 48px`, для фотографии в заголовке раскрытой панели — `sizes: 56px`. Это даёт браузеру запас разрешения для экранов высокой плотности при сохранении небольшого объёма загрузки.
- При проверке смотреть именно на опубликованную свёрнутую кнопку «Связаться с нами» и на фотографию после раскрытия панели: изображение должно совпадать, а детализация оставаться чёткой на телефоне и ПК.

## 3. Форматы и качество

- Для обычных фотографий сайта предпочтителен WebP; AVIF можно применять дополнительно, если есть fallback и подтверждена совместимость.
- JPEG/PNG-оригиналы не удалять автоматически: они могут быть нужны как исходники, fallback, прозрачные элементы или источники для дальнейшей обработки.
- Логотипы, графику с прозрачностью, пиктограммы и элементы фирменного стиля нельзя без визуальной проверки переводить в формат с потерями. Для них подбирать PNG/SVG/WebP с сохранением прозрачности и читаемости.
- Ориентир для оптимизированной карточной фотографии: около 100–150 KiB или меньше для выбранного размера. Это ориентир, а не повод ухудшать качество; решающими остаются визуальная проверка и фактический размер отображения.
- Не считать одну только конвертацию в WebP полной оптимизацией: большой WebP-файл без адаптивных размеров всё ещё может вызывать предупреждение PageSpeed.

## 4. Галереи и лайтбоксы

- Не уменьшать полноразмерный оригинал, который открывается пользователю в лайтбоксе.
- На странице показывать адаптивную обложку/миниатюру через `srcset` и `sizes`, а полноразмерный оригинал хранить отдельно и передавать лайтбоксу отдельным явным атрибутом/полем (например, `data-full-src`).
- Перед изменением общего lightbox-кода проверить все его потребители. Нельзя незаметно подменить оригинал миниатюрой или сломать открытие фотографий.
- Для карточек портфолио соблюдать также `PHOTO-MIGRATION-RULES.md`: не менять соответствие фотографий проектам, порядок и подтверждённые оригиналы ради оптимизации.

## 5. Загрузка и LCP

- Для изображения, которое действительно является LCP/главным визуальным элементом первого экрана, не использовать `loading="lazy"`; при необходимости применять `fetchpriority="high"` и корректный preload после проверки, что это именно LCP.
- Для изображений ниже первого экрана использовать `loading="lazy"` и `decoding="async"`.
- Не назначать `fetchpriority="high"` всем изображениям подряд.
- Всегда сохранять резервирование места через корректные `width`/`height`, чтобы не вызывать скачки макета.

## 6. Исключения

Исключение из `srcset` допустимо только если ресурс:
- SVG/векторный и уже оптимизирован;
- маленькая UI-иконка с отдельным файлом подходящего размера;
- декоративный CSS-фон, для которого выбран отдельный responsive-подход;
- имеет единственный фиксированный размер отображения, и его файл уже соответствует этому размеру.

Причина исключения должна быть очевидна из имени/назначения файла или кратко зафиксирована в комментарии/аудите. Большие фотографии без `srcset` не считать допустимым исключением.

## 7. Проверка перед публикацией

- Проверить все HTML-страницы и общие компоненты, а не только страницу, где добавлено фото.
- Проверить локальные ссылки на все варианты `srcset`, существование файлов и соответствие реальных размеров заявленным.
- Проверить, что `sizes` совпадает с фактической CSS-шириной изображения на mobile/tablet/desktop.
- Проверить, что браузер выбирает небольшой ресурс на мобильном устройстве, а не скачивает полноразмерный оригинал.
- Проверить PageSpeed для затронутой страницы и хотя бы главной; если изменён общий компонент или общий стиль изображений — повторно проверить все типы страниц.
- Не считать успешный Actions или факт наличия WebP доказательством оптимизации. Статус «готово» — только после проверки опубликованной страницы и отсутствия новых ошибок/ухудшения качества.

## 8. Важное ограничение существующих инструментов

Сборка GitHub Pages и подготовка ZIP для Timeweb автоматически запускают `maintenance/optimize-published-images.py` после подключения общих компонентов и до финальной проверки. Скрипт обрабатывает статические растровые `<img>` на всех HTML-страницах: создаёт адаптивные WebP-копии в `dist`, подключает `srcset`/`sizes`, сохраняет исходный URL в `data-full-src` и не меняет оригинальные файлы в репозитории. Уже вручную настроенные `srcset` сохраняются, а их исходный `src` фиксируется в `data-full-src`. Финальная проверка проверяет и оригиналы, и все варианты `srcset`.

Важно: сборочный скрипт автоматически обрабатывает статические HTML-изображения. Для изображений, которые создаются динамически JavaScript из JSON/данных, а также для CSS background-image, нужно отдельно подготовить адаптивные ресурсы и подключить responsive-механику; нельзя считать, что статический проход их автоматически охватывает. Для портфолио продолжать использовать его проверенную систему `srcset` и галерей, не менять порядок и соответствие фото. `maintenance/tools/convert-images-to-webp.mjs` по-прежнему создаёт WebP-копии в `assets/images`, но сам по себе не заменяет сборочный адаптивный проход.

**Короткое правило:** новое фото = проверка исходника → оптимизированные размеры → адаптивное подключение → проверка lightbox (если есть) → проверка опубликованной страницы и PageSpeed. Без этого фото не считается готовым к публикации.
