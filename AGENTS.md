## ТЕКУЩИЙ ЭТАП ПРОЕКТА: СОЗДАНИЕ СТРАНИЦ УСЛУГ

**Главная текущая цель:** подготовить на сайте отдельные содержательные страницы для самостоятельных услуг BARIBAL. Это текущий рабочий этап проекта, а не только косметическое обновление существующих страниц.

### Эталон оформления
- Страница автохимчистки: `plain-site/himchistka/index.html` — утверждённый пользователем визуальный эталон.
- Эталонные особенности: фоновые секции на всю ширину окна от левого до правого края; внутреннее содержимое в аккуратном центральном контейнере; чередование светлых и графитовых секций; отдельная проверка контрастности обеих тем; адаптация для desktop и mobile; заметные кнопки и читаемые подписи.
- Страница автовинила: `plain-site/avtovinil/index.html` — приведена к этому визуальному принципу. Сохранять тексты, фотографии, цену, гарантийные формулировки, FAQ, галереи, CTA, формы и обработчики, если пользователь отдельно не просит изменить содержание.
- Страница `plain-site/kuzov/index.html` сейчас является обзорной страницей направления «Защита кузова», а не отдельной подробной страницей для каждой технологии.
- При создании каждой новой страницы использовать химчистку как визуальное лекало, но адаптировать содержание под конкретную услугу. Не копировать нерелевантные тексты, цены, обещания, фотографии или FAQ с другой услуги.

### Как быстро включаться в работу
1. Прочитать этот файл полностью, затем посмотреть последние записи журнала.
2. Рабочая ветка — `main`; основной сайт — обычные HTML/CSS/JS в `plain-site/`. Не трогать `test-project` и не возвращать Vite в основной workflow.
3. Перед правками проверить существующие страницы, общие стили, навигацию, ссылки, CTA и формы. Для фотографий обязательно читать `maintenance/PHOTO-MIGRATION-RULES.md`.
4. Согласовать структуру и содержание новой услуги по подтверждённым данным. Не придумывать цены, сроки, гарантии, бренды материалов и технические свойства.
5. Новую страницу делать в отдельной папке `plain-site/<slug>/index.html`, если это самостоятельная услуга и пользователь согласовал отдельную страницу. Добавить корректные Title, Description, один H1, внутренние ссылки и навигацию; проверить сборку и опубликованный URL.
6. Сохранять общие элементы сайта и действующие механизмы модальных окон/форм. Не создавать новый механизм заявки, если можно использовать существующий.
7. Проверять обе темы и desktop/mobile. После коммита дождаться Actions для последнего SHA, затем проверить опубликованный URL. Успешный Actions сам по себе не доказывает корректность визуального результата.
8. После каждого этапа обновлять журнал: дата, что изменено, SHA, Actions run и что ещё требует проверки.

## Главное правило

**Работа НЕ выполнена, пока результат не проверен на опубликованном сайте.**
Наличие файлов в репозитории, записей в JSON, ссылок в HTML/JS, успешного коммита или зелёного GitHub Actions НЕ доказывает, что пользователь видит результат на сайте.

Никогда не писать «готово», «размещено», «всё отображается» или «должно быть на сайте», основываясь только на проверке исходников.

## Обязательная проверка партии карточек портфолио

Для каждой партии (например, 81–100) выполнять все пункты:

1. Проверить фактический список карточек на странице `plain-site/foto/index.html`: нужные номера должны соответствовать нужным карточкам, без сдвига индексов и пропусков.
2. Для каждой карточки проверить, что в её HTML действительно задана основная фотография (обложка), а не только данные галереи. Проверить, что путь к изображению существует и файл не пустой.
3. Проверить, что JavaScript действительно назначает/рендерит фотографию в карточку, если карточки формируются динамически. Не считать обработчик открытия модального окна назначением обложки.
4. Проверить JSON/данные галереи отдельно: номера карточек, пути и существование файлов. Это дополнительная проверка, она НЕ заменяет пункты 1–3.
5. Проверить workflow публикации: он должен копировать все нужные HTML, JS, JSON и изображения в итоговый каталог публикации. Успешный workflow подтверждает только сборку/деплой, но не отображение.
6. После деплоя открыть именно опубликованный URL страницы портфолио и проверить фактический результат для каждого номера партии. Проверить сетевые URL изображений/HTTP-ответы и отсутствие ошибок загрузки. Если есть возможность браузерной проверки — проверить и визуально, что изображения действительно видны.
7. Сверить опубликованную версию с последним коммитом и дождаться завершения именно соответствующего deploy run. Не путать старый успешный запуск с текущим.
8. Только после всех проверок сообщать, что партия опубликована и видна.

## Если проверка опубликованного сайта невозможна

Честно и прямо сказать: «Файлы/код проверены, но отображение на опубликованном сайте не подтверждено». Не делать вывод, что всё готово. Не просить пользователя часами доказывать отсутствие результата — сначала самостоятельно проверить опубликованный URL и исправить то, что можно исправить.
