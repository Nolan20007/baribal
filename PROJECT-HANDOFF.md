## 1. Текущая архитектура и правила работы

- Репозиторий: `Nolan20007/baribal`.
- Основная рабочая ветка: `main`.
- Ветка `test-project` не относится к рабочему сайту — не менять.
- Активный сайт — обычные HTML/CSS/JavaScript в `plain-site/`. Это основной источник страниц.
- Старый Vite/White/Vital вариант заброшен; не возвращать его в рабочий процесс и не использовать его сборку для проверки опубликованного сайта.
- GitHub Pages — тестовая/проверочная публикация; целевой хостинг — Timeweb.
- Старый Creatium-сайт использовать как источник содержания, перечня услуг и фотографий, но не копировать его старый дизайн.
- Проверять результат на опубликованном сайте и на телефоне/адаптивных ширинах. Успешный commit или Actions сами по себе не доказывают, что пользовательский интерфейс работает.
- Не удалять фотографии, служебные скрипты, данные заявок/отзывов и файлы хранения без проверки использования и явного согласования.
- Секреты, пароли, SMTP-данные и доступы не помещать в Git, документы репозитория или чат.

## 2. Публикация на Timeweb — как работает

Workflow: [Deploy BARIBAL to Timeweb](https://github.com/Nolan20007/baribal/actions/workflows/deploy-timeweb.yml).

- Запуск ручной: GitHub → Actions → Deploy BARIBAL to Timeweb → Run workflow → ветка `main` → подтверждение. Обычный push в `main` сам по себе не запускает Timeweb-деплой.
- Workflow проверяет PHP 8.4, зависимости Composer, синтаксис PHP/JS, собирает сайт из `plain-site/`, добавляет `assets/`, API, admin, lib и vendor, внедряет production social/canonical metadata, общие формы и оптимизированные responsive images, затем проверяет обязательные файлы и локальные ссылки.
- Артефакт сборки: `baribal-timeweb-site` (хранится 7 дней).
- Приватные файлы создаются из GitHub Secrets и выкладываются отдельно в `./baribal/baribal-private/`, вне `public_html`.
- Публичный сайт выкладывается в `./baribal/public_html/`.
- В workflow намеренно не используется destructive clean-slate; не включать очистку приватного каталога без отдельного анализа.
- После запуска смотреть именно итоговый статус workflow и логи каждого шага. Не объявлять деплой успешным, пока run не завершился с успехом.
- GitHub Pages workflow отдельный: не путать его с Timeweb.

### GitHub Secrets, необходимые Timeweb workflow

- `TIMEWEB_FTP_USERNAME`
- `TIMEWEB_FTP_PASSWORD`
- `TIMEWEB_SMTP_USERNAME` — должен быть ровно `zayavki@baribal-studio.ru`
- `TIMEWEB_SMTP_PASSWORD`
- `TIMEWEB_DB_HOST`
- `TIMEWEB_DB_NAME`
- `TIMEWEB_DB_USERNAME`
- `TIMEWEB_DB_PASSWORD`
- `BARIBAL_ADMIN_PASSWORD` — не менее 16 символов.

Значения секретов ассистент не видит и не должен просить присылать в чат. Workflow создаёт приватный `baribal-mail.json` с SMTP, DB и хешем пароля админки. SMTP host: `smtp.timeweb.ru`; получатель уведомлений: `info@baribal-studio.ru`.

- Созданы ящики:
  - `info@baribal-studio.ru` — единый ящик-получатель клиентских писем и автоматических уведомлений сайта.
  - `zayavki@baribal-studio.ru` — технический ящик/SMTP-отправитель уведомлений сайта.
- Пользователь проверил внутреннюю переписку между ящиками ранее, но в текущем тестировании доставка на `info@` не работает.
- В Timeweb DNS-редакторе видны две MX-записи:
  - `mx1.timeweb.ru`, TTL 600;
  - `mx2.timeweb.ru`, TTL 600.
- В панели также ранее видели A-запись `baribal-studio.ru → 92.53.96.225`, SPF, DKIM и DMARC. Нельзя считать их действующими публичными записями, пока не проверена авторитетная DNS-зона.
- Пользователь сообщил: тестовая заявка сохранилась в админке, но письмо не пришло на `info@`. Отправка тестового письма из ящика `zayavki@` на `info@` тоже не привела к появлению письма. Внешнее письмо с другого заведомо рабочего ящика на `info@` также не пришло. Следовательно, входящая почта сейчас не подтверждена/не работает. Сохранение заявки в админке не доказывает SMTP-доставку.
- Доступ к аккаунту REG.RU у пользователя появится позже; сейчас просить его менять там настройки нельзя.

### Что сделать, когда появится доступ к REG.RU

1. Сначала посмотреть, какие NS-серверы реально делегированы для домена и где находится авторитетная DNS-зона.
2. Снять/зафиксировать все текущие записи DNS (A, AAAA, CNAME, MX, TXT, SPF, DKIM, DMARC и прочие нужные сервисам) до любых изменений.
3. Сравнить действующую зону REG.RU с DNS-редактором Timeweb и официальными актуальными требованиями Timeweb.
4. Установить причину, почему внешние письма на `info@` не доставляются. Проверить MX и связанные SPF/DKIM/DMARC, а также состояние почтовых ящиков/домена в Timeweb.
5. Только после сверки внести минимальные точечные изменения. Не менять NS и не переносить домен без отдельной необходимости и согласования. Не удалять и не заменять MX наугад.
6. Для сайта направить A-запись на фактический IP сайта в Timeweb (перед изменением сверить IP с настройками сайта/хостинга, не полагаться только на ранее замеченный `92.53.96.225`). Не нарушить почтовые записи.
7. После DNS-переключения установить бесплатный Let's Encrypt SSL в Timeweb; не покупать платный SSL без необходимости.
8. Проверить сайт по `https://baribal-studio.ru`, редиректы HTTP→HTTPS и `www`/без `www`, формы, админку, изображения и страницы.
9. Провести отдельные тесты почты:
   - внешнее письмо на `info@`;
   - письмо из `zayavki@` на `info@`;
   - заявка через сайт: запись в админке и письмо на `info@`;
   - проверить входящие, спам и при наличии bounce/error — текст ошибки.
10. Не считать почту готовой, пока входящее письмо с внешнего адреса и уведомление формы реально не получены на `info@`.

**Безопасность:** до доступа к REG.RU не менять DNS, MX, SPF, DKIM, DMARC, A или NS. В панели Timeweb записи видны, но их публичная активность не подтверждена.
